# Telco Customer Churn Prediction — API Documentation

---

## 1. API Overview

The Telco Customer Churn Prediction API is a production-grade REST service built with FastAPI. It exposes endpoints for health checks, single-record predictions, batch predictions, and Prometheus-compatible metrics.

### Capabilities
- Predict churn probability for a single customer.
- Score batches of customers efficiently.
- Return interpretable feature contributions using SHAP.
- Report service health and model readiness.
- Expose metrics for monitoring and alerting.

### Content Type
All endpoints accept and return `application/json` unless otherwise noted.

## 3. Authentication

Authentication is not implemented in the current release. The API is intended to run inside a private network or behind an authenticating reverse proxy (e.g., API gateway with OAuth2, mTLS, or API keys).

### Recommended Production Setup
| Layer | Mechanism |
|---|---|
| Edge | TLS 1.2+ termination |
| Gateway | OAuth2 client credentials or API key |
| Service-to-service | Mutual TLS (mTLS) |

## 4. Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/health` | Service health and model load status |
| `GET` | `/ready` | Readiness probe for load balancers |
| `GET` | `/metrics` | Prometheus-compatible metrics |
| `POST` | `/predict` | Predict churn for a single customer |
| `POST` | `/predict/batch` | Predict churn for multiple customers |

| `Dependents` | string | Yes | `Yes` or `No` |
| `tenure` | integer | Yes | Number of months as customer |
| `PhoneService` | string | Yes | `Yes` or `No` |
| `MultipleLines` | string | Yes | `Yes`, `No`, or `No phone service` |
| `InternetService` | string | Yes | `DSL`, `Fiber optic`, or `No` |
| `OnlineSecurity` | string | Yes | `Yes`, `No`, or `No internet service` |
| `OnlineBackup` | string | Yes | `Yes`, `No`, or `No internet service` |
| `DeviceProtection` | string | Yes | `Yes`, `No`, or `No internet service` |
| `TechSupport` | string | Yes | `Yes`, `No`, or `No internet service` |
| `StreamingTV` | string | Yes | `Yes`, `No`, or `No internet service` |
| `StreamingMovies` | string | Yes | `Yes`, `No`, or `No internet service` |
| `Contract` | string | Yes | `Month-to-month`, `One year`, or `Two year` |
| `PaperlessBilling` | string | Yes | `Yes` or `No` |
| `PaymentMethod` | string | Yes | Payment method used |
| `MonthlyCharges` | float | Yes | Current monthly charge |
| `TotalCharges` | float | Yes | Total charges to date |

## 6. Response Schema

### 6.1 Single Prediction Response

```json
{
  "churn_probability": 0.82,
  "churn_prediction": true,
  "threshold": 0.5,
  "model_version": "1.0.0",
  "top_features": [
    {"feature": "Contract", "contribution": 0.21},
    {"feature": "tenure", "contribution": -0.15},
    {"feature": "InternetService", "contribution": 0.12}
  ]
}
```

#### Field Descriptions

| Field | Type | Description |
|---|---|---|
| `churn_probability` | float | Predicted probability of churn, range `[0.0, 1.0]` |
| `churn_prediction` | boolean | Binary prediction based on `threshold` |
| `threshold` | float | Decision threshold used for binary classification |
| `model_version` | string | Version or run ID of the loaded model |
| `top_features` | array | Top 3 features contributing to the prediction |

## 7. Error Responses

All errors follow a consistent JSON schema.

### Error Schema

```json
{
  "detail": "Human-readable error message",
  "error_code": "VALIDATION_ERROR",
  "request_id": "abc-123"
}
```

### Common Errors

| Status | Error Code | Description |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Request body failed schema or value validation |
| `422` | `UNPROCESSABLE_ENTITY` | Invalid field type or missing required field |
| `500` | `INTERNAL_ERROR` | Unexpected server or model inference error |
| `503` | `MODEL_NOT_LOADED` | Model not loaded; service unavailable for predictions |

### Example Validation Error

```json
{
  "detail": "Invalid value for 'Contract': expected one of ['Month-to-month', 'One year', 'Two year']",
  "error_code": "VALIDATION_ERROR",
  "request_id": "req-789"
}
```

## 11. Performance Considerations

### 11.1 Latency Targets
| Endpoint | p50 | p95 | p99 |
|---|---|---|---|
| `GET /health` | < 5 ms | < 10 ms | < 20 ms |
| `POST /predict` | < 30 ms | < 100 ms | < 200 ms |
| `POST /predict/batch` (100 records) | < 50 ms | < 200 ms | < 500 ms |

### 11.2 Throughput
- Single container instance: ≥ 100 requests/second for single predictions.
- Batch endpoint: designed for campaign list scoring; recommended batch size ≤ 1000.

### 11.3 Optimization Recommendations
- Preload the model once per worker at startup.
- Use batch prediction for bulk scoring instead of looping over `/predict`.
- Tune `MAX_BATCH_SIZE` based on memory and latency requirements.
- Scale horizontally behind a load balancer for high-traffic workloads.
- Consider ONNX export if sub-50 ms p95 latency is required.

### 11.4 Rate Limiting
Production deployments should enforce rate limiting at the API gateway:
- Single predictions: 100 requests/minute per client.
- Batch predictions: 10 requests/minute per client.

### 11.5 Timeout Guidance
- Set client request timeouts to at least 5 seconds for single predictions.
- Set timeouts to at least 30 seconds for batch predictions up to 1000 records.
